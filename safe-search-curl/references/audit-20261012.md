# safe-search 技能审查与修复记录（2026-10-12）

> 注：同日技能更名为 safe-search-curl（目录与全局引用同步更新），本文历史记录保留当时名称。

> 背景：联网检索策略从 AGENTS.md 全局规则抽出为 safe-search 技能后，经一轮外部安全审核，修复 fetch_clean.sh 的 SSRF 重定向穿透等项。本文档记录审核处置决策与验证方法，供后续演进参考。

## 审核条目与处置决策

| 级别 | 条目 | 结论 | 处置 |
|---|---|---|---|
| 高危 | urllib 自动跟随 3xx 且不复查目标，公网页面 302→169.254.169.254 可穿透首层 SSRF 检查（实测复现） | 成立 | **已修复**：自定义 SafeRedirectHandler，每次重定向目标重跑 check_host |
| 中危 | fake-ip 白名单（198.18.0.0/15）使"域名解析到内网"检查在本机永不触发 | 判断正确 | **部分采纳**：豁免保留默认（否则本机开箱全拦），每次抓取输出 [warn] 明示 DNS 层检查不生效、依赖代理转发策略兜底。未采纳环境变量开关方案：默认不豁免=本机不可用，[warn] 已满足"不误以为防护生效"的核心诉求 |
| 低危 | DNS rebinding TOCTOU：getaddrinfo 校验与实际连接是两次独立解析 | 成立 | **接受残余风险**：直连解析 IP 会破坏 https 证书校验，代价大于收益。SKILL.md 已标注 |
| 小 | 无 scheme URL 报"域名无法解析: "，有误导 | 成立 | **已修复**：自动补 https:// 并输出 [info] |
| 小 | script/style 正则不匹配属性值含 > 的标签 | 成立但极少见 | **不修**：已防住主要风险（内联 JS），换 HTMLParser 成本/收益不划算 |
| 小 | exit code 未区分 blocked/error | 属实 | **不修**：[blocked]/[error] 前缀对 agent 已足够 |
| 文档 | SKILL.md "已内置拦截（含 DNS 解析后检查）"表述夸大 | 成立 | **已改写**：明确拦截范围与两个已知边界 |

## 修复后防护边界（诚实版）

- 拦截范围：原始 URL + 每一次重定向目标的 host（字面 IP 直查；域名含 DNS 解析后检查）
- 边界 1：fake-ip 代理环境（本机）下所有域名解析到 198.18.0.0/15，DNS 层检查退化为 [warn]，兜底依赖代理转发策略
- 边界 2：DNS rebinding（校验时公网 IP / 连接时内网 IP）为接受的残余风险
- 手工 curl 注意：curl 默认也自动跟随重定向，重定向穿透风险同源

## 验证方法（可复用）

1. **302 穿透复现**：本机起两个 HTTPServer，A:8761 返回 `302 Location: http://127.0.0.1:8762/secret`，B:8762 返回 SECRET_INTERNAL_DATA
   - 无防护 `urllib.request.urlopen(A)` → 拿到 SECRET（穿透成立）
   - `build_opener(SafeRedirectHandler).open(A)` → `[blocked] 拒绝跟随重定向`（防护生效）
   - 提取脚本库代码测试：`awk '/^import /{f=1} f{print} /return super/{exit}' fetch_clean.sh > core.py`（heredoc 结构保证 import..class 段无顶层副作用，可直接拼接测试 harness）
2. 回归：字面内网 IP（127.0.0.1 / 169.254.169.254 / 192.168.1.1）、localhost/.local 首层拦截；example.com 正常抓取带 [warn]；http://github.com 重定向跟随且 [source] 显示最终 URL

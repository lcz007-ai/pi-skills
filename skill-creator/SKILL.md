# 技能创建器

把一段可复用的工作流固化成 skill。skill 是给 agent 的"按需加载的专业知识 + 配套脚本/资料"，不是新工具——只在任务匹配时才加载，避免长期占用上下文。

## 何时用

- 用户说"把这个流程做成技能""我想建个技能""怎么给 X 写 skill"
- 用户已有草稿，想改正文或触发描述
- 同一类任务在对话里反复出现，值得沉淀

## 三条核心原则

1. **简洁**：正文只说模型不知道、或容易做错的事，别复述系统提示里已有的工具说明。
2. **渐进披露**：元数据（name + description）常驻 → 触发时加载 SKILL.md 正文 → 需要时才读 references/、跑 scripts/。详情放 references，确定性动作放 scripts。
3. **description 是触发主开关**：模型只靠 name + description 决定用不用这个技能，必须同时写清"做什么"和"何时用"。

## 流程

### 1. 捕捉意图

先看当前对话里是否已包含要沉淀的流程（用过哪些步骤、踩过哪些坑、输入输出长什么样），有就直接提取，缺的再问。需确认：

- 这个技能让模型能做成什么？
- 什么话、什么场景应触发它？
- 期望的输出形式？
- 输出是否客观可验证（文件转换、取数、代码生成 → 值得写测试；文风、设计 → 人看即可）？

### 2. 访谈与补料

主动追问边界情况、输入输出格式、示例文件、成功标准、依赖。别急着写，先定下来。

### 3. 写 SKILL.md

frontmatter 至少两项：

- **name**：小写字母/数字/连字符，≤ 64 字符，无首尾或连续连字符。
- **description**：≤ 1024 字符。写"做什么 + 何时用"，可稍积极一点以对抗漏触发。对比：
  - 弱："如何给内部数据做仪表盘。"
  - 强："如何给内部数据做仪表盘。只要用户提到仪表盘、数据可视化、内部指标，或想展示任何公司数据，就用这个技能，哪怕没明说'仪表盘'。"
- （可选）`disable-model-invocation: true`：只允许 `/skill:名字` 手动调用。

目录结构：

```text
skill-name/
├── SKILL.md          必需：frontmatter + 指令
├── scripts/          可选：确定性 / 重复性动作的可执行脚本
├── references/       可选：按需读入的文档
└── assets/           可选：模板、图标等产出物素材
```

### 4. 写作要点

- **正文 < 500 行**；接近上限就再分层，并在正文指路"下一步读哪个文件"。
- **references 文件 > 300 行**就加目录（TOC）。
- 支持多领域时按变体拆分（如 `references/aws.md`、`gcp.md`），只读相关那份。
- 用**祈使句**。
- **讲清"为什么"**，少用 MUST / ALWAYS / NEVER 这类硬压——模型很聪明，给理由比给命令更稳。
- 定义固定输出格式时给出确切模板；举例用"输入 / 输出"对照。
- 引用配套文件用相对技能目录的路径。

### 5. 测试（Pi 版，不依赖 subagent）

Pi 没有原生 subagent，用**轻量手测**代替并行基线对比：

1. 写 2–3 条真实用户会说的测试 prompt（口语化、带细节），先给用户确认。
2. 逐条执行：
   - **带技能**：用 `/skill:名字 <prompt>` 强制加载，或正常对话看是否自动触发。
   - **基线**：同一 prompt，不带技能直接做。
3. 把两次结果并排给人看，问："这样对吗？要改什么？"
4. 记录对比（可存 `evals/evals.json`，先只写 prompt，断言后补）：

```json
{
  "skill_name": "example-skill",
  "evals": [
    { "id": 1, "prompt": "用户会真实说出的话", "expected_output": "期望结果", "files": [] }
  ]
}
```

可选自动化：Pi 有 `pi -p "<prompt>"` 一次性打印模式（见 Pi `docs/cli.md`）。可在临时目录装好技能后用它批量跑测试 prompt 替代手工；但"是否自动触发"仍建议人工确认。

### 6. 迭代改进（核心循环）

拿到反馈后：

1. **泛化，别过拟合**：技能要被用成千上万次，不能只为那 2–3 个样例打补丁。某个问题反复出现时，换个说法 / 换个思路，而不是堆更多 MUST。
2. **保持精简**：删掉没用的部分；读执行记录而不只看最终输出，看技能是否让模型做了无用功。
3. **解释 why**：把用户反馈背后的真实意图翻译进指令。
4. **找重复劳动**：如果每个测试用例里模型都自己写了同一个辅助脚本（如 `build_chart.py`），就把它固化进 `scripts/`，以后直接用。
5. **增量修改**：只改出问题的那部分，保留已验证有效的部分，别整篇重写——重写容易把已经能用的行为一起改坏。
6. **每条指令都要"挣其位置"**：说不清"它防止了哪种错误"的指令，删掉。
7. 每轮记一行"改了什么、为什么"，方便回滚和对比。
8. 改完重跑测试，重复直到用户满意、反馈为空、或不再有明显改进。

### 7. description 校准（可选）

description 决定触发准确率。做法：

1. 造约 20 条查询：~10 条 should-trigger、~10 条 should-not-trigger。
   - 要**真实具体**（带文件路径、列名、公司名、口语、笔误），别用抽象短句。
   - 负例要**近邻**："写个斐波那契函数"对 PDF 技能太容易，测不出东西；要用"关键词像、但实际需要别的功能"的查询。
2. 把这份集合给人 review、勾选增删。
3. （可选）用 `pi -p` 逐条跑，看是否实际触发该技能，统计触发率，据此改 description。
4. **两个指标都要看**：should-trigger 的命中率、should-not-trigger 的误触率，缺一不可。
5. **别把 description 写太窄**：为了压低误触而收窄措辞，会导致真该用时反而不触发；宁可略宽。
6. **和相邻技能划清界限**：措辞要能与相似技能区分，避免互相抢触发。
7. 把校准后的 description 写回 frontmatter，展示前后对比。

## 更新已有技能

- **保留原 name 与目录名**，别改成 `xxx-v2`。
- 安装目录可能只读，先复制到可写位置再改。
- 改前先快照一份旧版本，便于对比。
- **更新前先跑一遍现有测试用例**，确认没把已通过的行为改坏（回归）。
- 除非有明确理由，保留原 description 的措辞风格与触发范围。

## 分发（可选）

技能就是一个含 `SKILL.md` 的目录，复制到 `~/.pi/agent/skills/` 或项目的 `.agents/skills/` 即可；也可用 Pi package（npm / git）分发（见 Pi `docs/packages.md`）。

## 核心循环（再强调一遍）

定意图 → 写 / 改技能 → 用 `/skill:` 或对话跑测试、带基线对比 → 和人一起看结果 → 泛化改进 → 重复 → 满意后再校准 description。
